# The ring-buffer fix: the earlier recorded-noise route (ADPCM payload, tone path, and the 512-sample tone ring)

Purpose: a technical write-up of the route this project used before the DSP-generator (`docs/dsp-generator-route.md`) replaced it: playing a recorded, looped ADPCM noise file through the stock tone path, and the fix that removed audible clicks at 48 kHz by enlarging the DSP's tone ring. Kept here because it is a complete, independently useful method — carrying custom audio content into a locked CSR8670's DSP mix without any DSP code of your own — and because the ring-size fix is reusable by itself, including by the DSP-generator route that followed it.
Status / last verified: 2026-10-28. Everything marked **proven** was observed on the real speaker (firmware 3.0.3.6546) by instrument (recording + analysis) or by a quoted command result; **well-supported** is one inference beyond that; **hypothesis** is unconfirmed.
Read next: `docs/topics/audio-path-and-dsp.md` (the stock audio path), `docs/FLASH-PROTOCOL.md` (the mandatory gates before any flash), `docs/dsp-generator-route.md` (the route this one was superseded by).

## 1. Architecture

1. Only signed DFU images load on a locked CSR8670. This project's patch mechanism is a "hook" (a patched branch in the application-CPU firmware, e.g. the centre-button handler) that jumps into a "cave" of custom VM code placed in a small writable window plus an approved pool of otherwise-dead functions (`docs/topics/cave-and-hooks.md`). **Proven.**
2. The application CPU calls firmware "traps" (syscalls); `KalimbaSendMessage(id, w1, w2, w3, w4)` sends a message to the Kalimba DSP: AL = id, AH = w1, stack slots 0-2 = w2, w3, w4 (`docs/trap-abi.md`; `docs/message-task-abi.md`). **Proven.**
3. The Kalimba DSP runs the stock `sbc_decoder` application. Stock path: A2DP → RTP transform → Kalimba sink port 0 → SBC decode → mix → DAC (`docs/topics/audio-path-and-dsp.md`). **Proven/well-supported.**
4. Kalimba port 3 is the tone/voice-prompt input. The stock tone recipe, which this route reuses for custom content: `KalimbaSendMessage(0x1072, rate)` to set the rate, `StreamKalimbaSink(3)` as the sink, `TransformAdpcmDecode(source, sink)` to decode, `TransformStart` to begin. A transform is mandatory — the same bytes sent straight to the port were silent; through `TransformAdpcmDecode` they were loud. **Proven.**
5. Inside the DSP, a copy timer (period in microseconds = 128,000,000 / rate) moves up to the ring's sample count from the port-3 circular buffer into the **tone ring**, a structure `{size, read pointer, write pointer}` in DSP data memory; the mixer reads the ring. **Proven** (read back from the device; see section 6).
6. Port rules, carried over from this project's broader port-3 findings: a data chunk lasts `size * rate` seconds (not a few seconds — 219 s at a 2 kHz rate on a 219,528-byte file); checking whether the transform is still busy is reading one flag, not stopping it; never call the "stop" trap on the handle the start call returned (it panics the device); never speak while the transform holds port 3.

## 2. What the audio content actually is

The only files a locked CSR8670 can stream through `StreamFileSource` are "narrow" files (a flag Bose's filesystem format marks), of which this image ships exactly two: the voice-prompt file and a ringtone/phrase file. The audio is ADPCM-encoded (not raw PCM — the stock decoder is `TransformAdpcmDecode`), generated by this project's own encoder (`tools/adpcm.py`, `build/payload/make_narrow_payload.py`) from a brown-noise source built at the target sample rate and loop length.

**Delivery needed two images, because the signed-filesystem blind-byte technique (`docs/topics/dfu-and-signing.md`) is not large enough to carry a multi-second audio loop.** Instead, a one-time "writer" image stages the payload inside the voice-prompt file's own slot (temporarily degrading the stock voice prompts), then performs a **runtime write to the speaker's second flash partition** — not a signed-DFU edit, but a write issued by the running application itself over a normal USB connection, the same mechanism Bose's own firmware uses to deliver language packs. This is, by this project's own risk assessment, **the single highest-risk operation in this whole project**: unlike every signed-DFU edit, which the device's own verification can reject before anything is written, a misaligned runtime partition write has no such gate and its failure mode is an unrecoverable brick, not a recoverable wedge (`docs/partition-route.md` "What makes it unsafe"). A second, "product" image then replaces the writer, restores the stock voice prompts, and plays the staged payload through the cave described below.

## 3. The symptom and its root cause

**Symptom.** Occasional audible clicks, roughly 0.3-1.8 per minute at a 48 kHz DAC rate, confirmed by an automated listening instrument (`tools/click_detect.py`, built for this project) as quantised timeline insertions of about 2-4 ms in an otherwise-looping recording. **Proven** (measured, repeatable).

**Root cause (well-supported, not fully proven as a single root cause).** The DSP's tone ring is small — a classic producer/consumer circular buffer with a fixed sample count — and its fill level sets a "lead" time (the cushion between the copy timer refilling it and the mixer draining it). At 48 kHz a 256-sample ring gives only about 2.6-5.3 ms of lead; any stall on the application CPU longer than that underruns the ring, and the DSP replays or drops a fixed-size stale block, which is heard as a click. The same sample count gives roughly double the lead time at 32 kHz, which is why lowering the rate was the first thing that worked — but 48 kHz was the quality target, so the project went looking for a way to enlarge the ring itself rather than lower the rate.

Many other explanations were tried and ruled out first (poll rate, Bluetooth, USB/charger activity, stock timers, deep sleep, rebuild delay, the payload's own waveform and loop-seam shape, a volume-poke timing issue) — none of them changed the click rate. The underlying application-CPU stall that eventually underruns the ring was never identified; the ring enlargement is a proven, effective workaround for its symptom, not a fix for its cause.

## 4. Reading the DSP's own memory (how the ring was found)

Because there is no output channel from the application CPU except audio and a USB console that cannot be read back directly, this project read the DSP's internal state with a **spoken census**: a small cave routine PEEKs a DSP data-memory address and speaks the 16-bit result back as a sequence of battery-percentage voice prompts, one per octal digit (digit *d* → (d+1)×10%), with a seventh digit as a checksum (sum of the six digits mod 8) so a misheard or silent slot is caught rather than silently accepted. A laptop microphone recording is decoded slot-by-slot with a speech recognizer. The same two DSP messages used for this read are a general-purpose PEEK/POKE pair the stock `sbc_decoder` application answers for debugging (see `docs/dsp-generator-route.md` section 2 for the exact message IDs and argument layout — the generator route reuses this same interface). This surfaced the ring's structure, its base address, and that a contiguous block of data memory immediately after it was free (read as zero, and referenced by no code in the image).

## 5. The fix

Three DSP data-memory writes (via the POKE message), issued by the cave immediately after the rate-set message empties the ring and before the "go" message starts playback:

```
POKE ring.write_pointer := new_base
POKE ring.read_pointer  := new_base
POKE ring.size          := new_base      # (so the new ring spans new_base .. new_base + new_size)
```

**Order matters.** Writing the size field first — before the pointers are moved off the old ring's address range — makes the ring's modulo arithmetic briefly treat part of the ring's own control structure and an adjacent lookup table as if they were inside the (now larger) ring, corrupting them. Writing both pointers to the new base first, then the size last, avoids this. This was established by static analysis of the copy and mixer routines (which reload their modulo length from the size field on every call) before being proven safe on hardware.

The new base and size were chosen from the free data-memory region the census found: large enough to roughly double the available lead time at 48 kHz (to about 8-10.6 ms), and sized so the new ring occupies that free region exactly, overlapping no code or table the stock application reads.

**Non-persistence.** This is a data-memory write, not a filesystem edit — it never touches flash. The DSP's own program reloads at every cold start (each time playback begins from idle), which resets the ring to its stock size and location, so the three pokes are reissued every time playback starts. There is no flash-corruption risk from getting this wrong: recovery from a bad write is simply turning the noise off and on, or a power cycle.

## 6. Verification

**Instrument.** `tools/click_detect.py` records the speaker with a laptop microphone, aligns each loop iteration to the known payload, builds an empirical per-loop template, and reports: STEP events (persistent timeline shifts inside a loop, > 1.2 ms — the click signature), the loop-seam gap and its high-frequency energy (a separate, unrelated artifact from the loop restarting slightly early), and BURST events (short energy spikes). It is gain-independent and expects the recording to start in silence.

**Result.** With the ring enlarged, two independent recordings covering a combined ~15 minutes of continuous 48 kHz playback measured **zero STEP events** (versus 0.3-1.8 per minute before the fix, and versus zero at the fallback 32 kHz rate used as a clean baseline). The loop-seam artifact and its background burst rate were unchanged — enlarging the ring removes the underrun clicks specifically, not every artifact in the loop. This is an instrument result; say "removed the timeline steps," not "fixed all audible clicks," when citing it.

## 7. Pitfalls (reuse these on a similar project)

1. A console/debug event ID is not safe just because you have never seen it used. One event triggered a boot-mode change that made the speaker re-enumerate as a bare recovery-mode USB device, cured only by a physical USB replug; another entered a loader mode. Stick to IDs already known to be handled normally, and after sending any console event, check the USB device's own last-arrival/enumeration timestamp — a silent reset does not always show up as the device disappearing.
2. A DSP reply handler that receives "which word is this" as an argument must reload that argument fresh from its own call frame; reusing a stale copy returns the same (wrong) value for every address queried.
3. Sending too many delayed messages from one handler in a short window can exhaust the firmware's small message pool and reset the device; back off to fewer, and confirm the device is still enumerating after each batch.
4. A read of zero is not proof an address is free or unused — a freshly (re)loaded DSP image reads zero in regions it simply hasn't initialized yet. Cross-check against the DSP build's own linker map or disassembly before assuming a region is free.
5. Offline simulators for this chip generally do not model DSP (Kalimba) memory at all — hardware read-back is the only way to confirm anything about DSP state.
6. Do not trust the first reading of any value obtained this way without the check-digit (or equivalent) protection; the first unchecked attempts at this census returned wrong values more than once before the protocol above was in place.
7. Lowering the sample rate trades quality for a larger lead time "for free" without touching the ring at all — useful as a fallback while debugging, and as a sanity check that the mechanism (not some unrelated cause) is responsible for the click rate.

## 8. Relationship to the DSP-generator route

This ring enlargement is not specific to playing back a recorded file — it is a general property of the stock tone-mixing path on this chip family, and it was carried forward unchanged into the DSP-generator route that superseded recorded playback (`docs/dsp-generator-route.md`): the generator writes its samples into the same enlarged ring. A project that only needs to deliver pre-recorded or externally-sourced audio content (not synthesize it inside the DSP) can stop at this document and section 2's blind-byte delivery method; a project that wants to generate audio inside the DSP itself should read the generator route next.

## 9. Reproducing this route without the vendor toolchain

Unlike the DSP-generator route, this route needs no DSP assembler at all — both images are pure signed-filesystem edits. `build/patches/` ships the already-computed byte-diff for both: `probe346_writer_from_stock_3.0.3.6546.patch.json` (the writer, flash first) and `probe367_product_from_stock_3.0.3.6546.patch.json` (the product, flash second, only after the writer reports a successful write). Apply either with `build/patches/apply_patch.py` against the same verified stock firmware download described in `docs/clean-room-rebuild.md` — no ADK, no vendor filesystem-signing tool, pure Python standard library, each step hash-verified before anything is written. See the README's "Reproducing this yourself" section for the exact command.
