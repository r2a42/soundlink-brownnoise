# The DFU signature scheme — final state

Purpose: the complete, as-established mechanics of this device's signed-filesystem check, and the write channel this project uses — stripped of the session-by-session research log that found it (which contained several corrected false starts). For the plain-language summary and the facts table, read `docs/topics/dfu-and-signing.md` first; this page is the derivation behind it.
Status / last verified: 2026-10-28. Everything below reflects the final, cross-checked state; nothing here is a withdrawn or superseded claim.

## 1. The scheme, from the vendor's own source and the device's own behavior

- The filesystem area is signed with 1024-bit RSA, public exponent e = 3, no padding. Verification — the only operation the device itself performs — is raw `block^3 mod n`; signing (which this project never does, and does not need to do) uses the private exponent.
- The modulus `n` is not printed anywhere convenient in the firmware; it is recoverable offline from any set of several official signed firmware releases via a GCD attack (`tools/recover_modulus.py`), since every release's signature satisfies `S^3 mod n == B` for the same `n`. Recovering it is recovering the device's own *public* verification key, which is inherently non-secret by definition — it does not grant any signing capability (see section 3).
- The signed `block` is not the filesystem content directly. It is built by feeding `digest(4 bytes) + filesystem body` (minus the area's final word) through **eight independent, interleaved, standard-MD5 chains**, each initialized to the normal MD5 IV. The content is split into 64-byte chunks; chunk *k* feeds chain *k mod 8*. Within each chunk, the hash reads only the chunk's **first 34 bytes** as its message words (a 16-bit sliding window over the chunk's bytes) — the remaining 30 bytes of every 64-byte chunk never enter the hash at all. The final content tail (if any) is padded MD5-style and folded into the chain rotation. The eight chains' final states (128 bytes) are the signed block; the device recomputes this same block from the content it receives and checks it against the stored signature.
- A second, separate 32-bit digest field is also checked by the device's loader. It is **GF(2)-linear** (a CRC-family checksum, not a cryptographic hash): flipping bit positions in the input flips a fixed, predictable, position-dependent set of output bits, independent of the rest of the content. The vendor's own filesystem-build tool reproduces this digest exactly and recomputes it on any edit, which makes it usable as an oracle without needing to know its internal construction.
- A third check, a 16-bit XOR redundancy over the filesystem body, must land on zero or the vendor's own build tool silently drops the filesystem as "redundant" rather than emitting a container.

## 2. What this means for custom content

Because the signature hash reads only the first 34 of every 64 content bytes, the remaining **30 bytes of every 64 ("blind bytes")** can hold arbitrary content without changing the signed block at all — so an existing, validly-signed filesystem's original signature stays valid over an edit confined to those bytes. No forged signature, no private key, and no break of RSA or MD5 is involved or needed: the stock image's own signature is simply never invalidated, because the edit never touches anything the hash reads.

This is a bounded capability, not a general one: it can only modify roughly 45% of the byte positions of a filesystem Bose has *already* validly signed (such as the official firmware download), inside specific byte ranges, and it cannot produce a validly-signed image from unsigned or arbitrary content, nor forge a new signature for content outside those ranges. Two further checks must also be kept passing:

1. **The 32-bit digest** must stay byte-identical. Because it is linear, the change it produces from a set of candidate edits can be measured against the vendor build tool (used purely as a black-box oracle — no internal knowledge of the digest's construction is required) and cancelled out with a small set of compensating edits, found with ordinary linear algebra (a GF(2) solve) over a pool of otherwise-unused blind-byte positions.
2. **The 16-bit body XOR** must land on zero; any residual parity is corrected the same way, by flipping bits at pool positions.

`tools/fsedit.py` automates all of this: given a list of desired edits (all within the blind-byte ranges), it rebalances the XOR, solves for the digest-compensating flips, applies everything, and verifies the result (digest byte-identical, signature block unchanged, XOR zero, every container checksum valid) before handing back a filesystem ready to repack into a DFU. This has been proven on hardware with arbitrary chosen content — a filesystem edited this way was flashed and accepted by a real, unmodified device, and a readback confirmed the edit persisted exactly as built.

**On the recovered modulus specifically:** knowing `n` only lets you verify offline whether a candidate signature/content pair would pass — the same check the device performs. It does not let you produce a *new* valid signature for content Bose never signed; that would require the private exponent `d`, which has never been obtained and is not derivable from `n` and `e` alone at this key size by any method used or attempted here. The blind-byte technique above is the entire reason this project can modify a signed image without that private key — it is not an optional precaution.

## 3. Doors that were tried and are closed

- **The stack area.** Carries only a CRC-32 (no RSA signature, no digest field) in its own header. A CRC-valid edit to it was still rejected by the loader at the manifest stage. The loader is therefore checking it against some reference not visible anywhere in the plain image — most likely the stack's own signature checked against a vendor public key embedded in the loader at build time, which is never part of any DFU payload and so cannot be reached over USB. This door is closed, not just untried.
- **The unsigned PS (persistent-store) areas.** Same outcome: CRC-32 only, no signature or digest field, and a CRC-valid one-byte edit was still rejected the same way as the stack. Closed for the same reason.
- **A collision or preimage attack on the 8-chain MD5 construction**, which would in principle allow a *new*, validly-signed filesystem built from content the hash's blind window alone could not reach, was considered as a fallback and explicitly not pursued once the blind-byte route above proved sufficient for this project's goal. It was never attempted, let alone demonstrated, and nothing in this project depends on it.

## 4. Recovery

Downloading the official stock firmware and leaving DFU mode always restores the device to a known-good state; the loader will always accept a validly signed official image. This is the standard recovery path after any rejected or malformed custom image, and was used routinely during this project's development. See `docs/FLASH-PROTOCOL.md` for the exact, mandatory sequence — read it before attempting any of the above.
